Chapter 4 · A spatial application of generative objects

Spatial Organization with node-mixin

Generative objects do not have to be geometric. When they represent parts of a spatial assembly, however, a coordinate system makes their relationships much more expressive. Adhoc's scene-graph library supplies this functionality through node-mixin.

Source note. The class name node-mixin, the origin and rotation inputs, and the transformation macros come from adhoc-scene-graph. The quaternion function qrotation comes from 3d-math. The shaft assembly and its global-coordinate transformation have been tested in a running RGN-GEO image after corrections to the scene-graph coordinate-conversion functions. Package imports or qualification are assumed: defobject from Adhoc, node-mixin and globally from the scene-graph package, and vec3 and qrotation from 3d-math.

4.1 From Generative Objects to Spatial Nodes

The source calls the class node-mixin; when discussing its role we may simply call an instance a node. It is a generative superclass that supplies spatial inputs and computed transformations. It does not replace the general generative object model: ordinary non-spatial objects still use defobject without inheriting from it.

(defobject positioned-shaft (node-mixin)
  :inputs ((length 100))
  :attributes
  ((local-coordinate (vec3 100 0 0))))

Here positioned-shaft inherits spatial behavior from node-mixin while declaring its own length input. The ordinary attribute local-coordinate is a point at (100, 0, 0), expressed in the shaft's own coordinate system. This is class inheritance, not component composition; an assembly can subsequently contain an instance of this class.

The implementation also has graphics-related properties, but those are not needed to understand the spatial model.

4.1.1 Top-Level Nodes and Scene Registration

In a running Regen environment, creating a top-level node-mixin instance normally adds it to the default scene graph. If the node has graphical representation, it then appears in the graphics editor. Generative child components are not independently registered as top-level scene nodes.

;; Create a top-level node in the default scene:
(make-instance 'shaft-support)

;; Create a detached node without adding it to the scene graph:
(make-instance 'shaft-support :scene nil)

;; Equivalent ordinary-symbol initialization argument:
(make-instance 'shaft-support 'krma:scene nil)

Both explicit nil forms suppress the side effect of adding the new top-level instance to the scene graph. The :scene and 'krma:scene initarg names are distinct Lisp symbols, but this initialization protocol supports both. The instance still exists and can be used for computations without being registered in the displayed scene. A top-level scene node is retained by the scene until removed; being graphical is not a prerequisite for membership.

4.2 Origin: Position in a Parent Frame

The origin input gives the position of the child's coordinate-system origin expressed in its parent's coordinate system. The origin of the child's own local coordinate system is always (vec3 0 0 0); its origin input is not a point expressed in that local frame. In the source, its initial expression is (vec3 0 0 0). That position is a three-dimensional vector, rather than three unrelated scalar inputs.

(defobject positioned-shaft (node-mixin)
  :inputs ((length 100)))

(defobject shaft-support (node-mixin)
  :inputs ((shaft-offset 25))
  :components
  ((main-shaft :type 'positioned-shaft
               origin (vec3 (the shaft-offset) 0 0))))

The provided-input expression origin (vec3 (the shaft-offset) 0 0) positions the child shaft at an offset determined by the assembly's shaft-offset input. It is another example of generative composition: the containing object specifies a relationship that determines the child object's input.

Here and below the vector constructors and angle expressions are shown in the same general style as the libraries' source; the examples use an assumed package context rather than a complete application initialization sequence.

4.3 Rotation: Orientation with Quaternions

Coordinate systems can be rotated about their origins. The rotation input expresses the orientation of the child's local coordinate system relative to the parent. Its default in node-mixin is the identity quaternion, (quat 0 0 0 1).

3dm:qrotation constructs a quaternion from a rotation axis and angle. For example, a quarter-turn about the Z axis can be expressed as:

(qrotation (vec3 0 0 1) (/ pi 2))

The first argument is the axis vector; the second is the rotation angle in radians. The mathematical value (/ pi 2) represents 90 degrees. This example introduces quaternion construction without requiring the reader to manipulate quaternion components directly.

In the scene graph, a rotation-matrix attribute derives a transformation matrix from the quaternion, and the node's local matrix combines rotation and translation. Thus a rotation input participates in the node's spatial calculations.

4.4 Spatial Generative Composition

A component's origin and rotation can be specified using provided-input expressions. The assembly positions the shaft 25 units along its X-axis and gives the shaft a quarter-turn about Z:

(defobject shaft-support (node-mixin)
  :inputs ((shaft-offset 25))
  :components
  ((main-shaft :type 'positioned-shaft
               origin (vec3 (the shaft-offset) 0 0)
               rotation (qrotation (vec3 0 0 1) (/ pi 2)))))

The support itself retains the default identity rotation. The main-shaft component has an origin of (25, 0, 0) in the support's coordinate system, and its own local axes are rotated by the quaternion. A rotation of the shaft about its own origin does not move that origin; it changes the positions of other points defined in the shaft's local frame.

4.5 From Local to Global Coordinates

The shaft-support places the child shaft's origin at (25, 0, 0) in the support's frame and rotates its local X-axis 90 degrees about Z. The following was tested in a running RGN-GEO image with the corrected scene-graph coordinate-conversion functions:

(defobject positioned-shaft (node-mixin)
  :inputs
  ((length 100)))

(defobject shaft-support (node-mixin)
  :inputs
  ((shaft-offset 25))
  :components
  ((main-shaft
    :type 'positioned-shaft
    origin (vec3 (the shaft-offset) 0 0)
    rotation (qrotation (vec3 0 0 1) (/ pi 2)))))

(defun test ()
  (let* ((assembly (make-instance 'shaft-support))
         (shaft-object (send assembly main-shaft))
         (self shaft-object))
    (list
     (the origin)
     (globally (vec3 100 0 0)))))

(test)
;; => ((VEC3 25.0 0.0 0.0)
;;     (VEC3 25.00000000000002 100.0 0.0))

(the origin) reads the shaft's provided input: the position of its local origin in the support's frame, (25, 0, 0). By contrast, the point (vec3 100 0 0) in globally is expressed in the shaft's own frame. The transform rotates that point onto positive Y and translates it by the shaft's parent-relative placement. Its global position is approximately (25, 100, 0); the tiny difference in the printed X coordinate is ordinary floating-point rounding.

;; The globally macro expands to:
(transform-to-global-coordinate (vec3 100 0 0) self)

The globally macro uses self as its source frame. transform-to-global-coordinate should apply the node's global-matrix to convert a local point into global coordinates; its inverse, transform-from-global-coordinate, should apply inverse-global-matrix. The general transform-coordinate-from-to operation converts coordinates from its specified source frame to its destination frame. The three conversion implementations were corrected before the test above.

A global coordinate system is not necessarily identical to the root object's local coordinate system; the scene-graph API distinguishes those concepts.

4.5.1 Reading an Attribute Versus Transforming Its Coordinate

Package note: Here locally means adhoc-scene-graph:locally, not the Common Lisp special operator cl:locally. The example assumes that the scene-graph macro is imported into the current package.

For a coordinate-valued attribute in the child's own frame, the simply reads the value, whereas locally converts it into the frame of self. For example, if positioned-shaft also declared (local-coordinate (vec3 100 0 0)) under :attributes:

(let* ((assembly (make-instance 'shaft-support))
       (self assembly))
  (the main-shaft local-coordinate))
;; => (VEC3 100.0 0.0 0.0)

(let* ((assembly (make-instance 'shaft-support))
       (self assembly))
  (locally main-shaft local-coordinate))
;; Expected: approximately (VEC3 25.0 100.0 0.0)

The first expression reads the value in the shaft's own coordinate system. The second asks for that same point expressed in the support's coordinate system. Unlike the globally transcript above, this locally example is an expected result, not a separately recorded runtime test.

Do not use (locally main-shaft origin) to test a child-to-parent conversion: the shaft's origin input is already expressed in the parent's frame, while locally treats the referenced attribute's value as child-local. To convert the child's actual local origin, use a point of (vec3 0 0 0) in the child's frame.

4.6 A Small Spatial Assembly

The complete example has only two spatial objects: an unrotated support and its shaft. The support places the shaft 25 units along X and rotates it 90 degrees about Z. The shaft defines a local point 100 units along its own X-axis.

(let* ((assembly (make-instance 'shaft-support))
       (shaft-object (send assembly main-shaft))
       (self shaft-object))
  (globally (the local-coordinate)))

The expression follows the component, reads its local-coordinate attribute, and asks for that point in global coordinates. With the corrected transformations, the result is expected to be approximately (25, 100, 0), consistent with the independently tested explicit-point example in Section 4.5. It combines ordinary attributes, component provided inputs, quaternion rotations, reference chaining, and coordinate transformations without requiring a rotation of the containing assembly.

4.7 What Comes Later

This chapter introduces spatial organization as an application of generative composition, not as a complete geometry course. Later topics include detailed transformations between any two node frames, the as macro, more advanced uses of locally, quaternion operations, geometry defined in local frames, and dependency/invalidation behavior when placements change.

As in earlier chapters, this is a conceptual progression: the object model and its declarative attribute semantics come first; spatial representation is a powerful but optional capability built on top of them.
