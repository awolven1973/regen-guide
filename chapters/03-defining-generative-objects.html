Defining Generative Objects

This chapter introduces actual defobject syntax, using forms documented in the Adhoc implementation's test suite. A generative object declares properties and relationships; the system evaluates those declarations as needed.

Source status. The forms and operations below are based on Adhoc's tests and its implementation. The examples have not been executed in a live Regen image as part of writing this chapter. Their meaning and portability should be confirmed against the version used in Regen. Use these as introductory patterns, not a complete language reference.

3.1 The Shape of a defobject Definition

A defobject form names a generative CLOS class, identifies its direct superclasses, and declares attributes. The first examples use the three essential attribute kinds discussed in Chapter 2. They are not the only possible attribute kinds.

(defobject name (superclass ...)
  :inputs (...)
  :attributes (...)
  :components (...))

This is a structural illustration rather than a runnable definition: name, superclass, and the ellipses stand for declarations. The empty superclass list () is valid. A definition need not use all three sections.

The declarative character is important: the expressions attached to attributes establish relationships in the model, not a script of instructions for a caller to invoke in a particular sequence.

3.2 A First Object with Inputs

The following is a small, standalone example of a generative object describing a rectangular plate through two configurable dimensions.

(defobject rectangular-plate ()
  :inputs
  ((length 10)
   (width 5)))

(let ((plate (make-instance 'rectangular-plate)))
  (send plate length)) ; => 10

Inputs establish values from which other properties can be derived. In this form, both input declarations provide expressions supplying initial values. The test suite establishes the same basic pattern with single-letter names and make-instance.

These dimensions are intentionally abstract numbers; units, dimensions, and geometric representations are subjects for later chapters.

3.3 Ordinary Attributes and Declarative Computation

An ordinary attribute can express a computed relationship. Here the plate's area is declared in terms of its dimensions.

(defobject rectangular-plate ()
  :inputs
  ((length 10)
   (width 5))
  :attributes
  ((area (* (the length) (the width)))))

(let ((plate (make-instance 'rectangular-plate)))
  (send plate area)) ; => 50

The area expression encodes part of the model's design intent: area is determined by length and width, rather than maintained manually as an unrelated number. The (send plate area), (the length) and (the width) forms use Adhoc's attribute-reference syntax.

The expression still executes Common Lisp computation. Declarative programming does not prohibit arithmetic or procedural code; it changes which relationships the programmer is responsible for specifying.

3.4 Reading Generative Attributes and Reference Chaining

Regen provides attribute-reference forms for reading the properties of generative objects. The two fundamental forms differ in how the starting object is supplied:

(send plate area)

(let ((self plate))
  (the area))

The name send reflects a message-passing paradigm: the attribute name is treated as a message sent to an object, requesting the value of that attribute. In a reference chain, each successive name is a message directed to the object produced by the preceding access. This is the conceptual model behind the notation; as explained in §3.4.3, simple chains are implemented by macro expansion into CLOS slot-value accesses rather than by a separate message-dispatch mechanism.

send starts with an explicit object expression, such as plate. This use of the is distinct from the standard Common Lisp cl:the special operator used for type declarations. The adhoc:the form expands to (adhoc:send adhoc:self ...). An attribute body ordinarily has a current object bound to adhoc:self, making adhoc:the particularly convenient there. Note that “Adhoc” is the name of Regen’s KBE kernel: Another Declarative Hierarchical Object-Centric [CLOS customization]. Packages that use Regen features including geometry shadow a number of Common Lisp symbols, and these packages that use Regen will not require you to qualify symbols with "adhoc:".

3.4.1 Reference Chaining

An attribute reference need not stop after one name. Reference chaining follows a sequence of named attributes, using the value obtained at one step as the object for the next step. This is especially useful when a generative object contains other generative objects.

For example, once an instance of the shaft-assembly defined in §3.5 has been created, its shaft's length can be read directly:

(send assembly main-shaft length)

(let ((self assembly))
  (the main-shaft length))

Both expressions begin with the assembly. The first name, main-shaft, identifies a component whose value is a shaft object; the second name, length, identifies an input of that shaft. The result is the shaft's length, not the component object itself.

Compare the expressions with their two-step equivalent:

(let ((shaft-object (send assembly main-shaft)))
  (send shaft-object length))

Chaining avoids naming intermediate objects when all that matters is the property at the end of the path. A longer chain can traverse multiple nested components. Adhoc's tests include expressions such as (send assembly-object child grandchild attribute), demonstrating that a chain is not limited to two names.

3.4.2 What a Chain Means

Each name in a reference chain is interpreted relative to the object reached by the preceding step. A chain therefore expresses navigation through the generative object model, not a single flat name or a Common Lisp package-qualified symbol. The intermediate steps must yield objects on which the next property can meaningfully be requested.

Chaining is also different from inheritance. Inheritance determines which attributes an object can possess through its class; reference chaining navigates from one object to another through attribute values, frequently through components. Later chapters will discuss cases in which attributes other than components supply object references.

Reference expressions can appear inside other attribute computations and provided-input expressions, making them a basic notation for expressing relationships across an assembly. The detailed rules for evaluation, dependency tracking, assignment, and invalidation belong in the subsequent chapters.

3.4.3 Reference Chaining and CLOS Slots

send and the are macros, not a separate object-access runtime. For a simple chain of attribute names, send expands into nested Common Lisp slot-value forms. For example:

(send assembly main-shaft length)

;; Equivalent expansion for this simple chain:
(slot-value (slot-value assembly 'main-shaft) 'length)

Likewise, (the main-shaft length) expands through (send self main-shaft length), and therefore to the same nested slot-value accesses starting from self. More advanced forms accepted by send can also aggregate object lookup using indices or variably named references; those are outside the scope of this first example.

The underlying attribute system is built on the Common Lisp Object System (CLOS) Metaobject Protocol. Inputs, ordinary attributes, and components are represented through specialized slot-definition metaobjects, rather than through an unrelated attribute lookup mechanism. Adhoc defines corresponding direct and effective slot-definition classes, selected by methods such as direct-slot-definition-class and effective-slot-definition-class on its generative metaclass.

Consequently, an ordinary-looking slot-value access can invoke Regen/Adhoc-specific behavior through the CLOS slot-access protocol, notably slot-value-using-class. This is where computed attribute evaluation and other specialized access semantics can be implemented. The nested expansion describes how the reference is expressed; it does not imply that every attribute is an independently stored CLOS slot whose value is simply fetched without computation.

This connection to CLOS is fundamental: attribute definitions are part of the class's metaobject structure, while the ordinary Lisp slot-access interface remains available to the program. We'll examine the slot-definition classes and evaluation protocol in more detail later.

3.5 Composition

Objects may specify constituent generative objects as components. The following example introduces a shaft and an assembly that contains it:

(defobject shaft ()
  :inputs ((length 100)))

(defobject shaft-assembly ()
  :components
  ((main-shaft :type 'shaft)))

(let ((assembly (make-instance 'shaft-assembly)))
  (send assembly main-shaft length)) ; => 100

The main-shaft component is declared with a :type expression. The nested send form follows the component relationship to read the shaft's length. Here the child simply uses its own input's initial value. This establishes composition: one object contains another, rather than inheriting from it.

3.5.1 Generative Composition

Generative composition goes further. A component specification can provide an expression for an input of the resulting child object. This establishes a relationship between the containing object's attributes and the child's attributes, rather than merely declaring that the child exists.

(defobject shaft ()
  :inputs ((length 100)))

(defobject shaft-assembly ()
  :inputs ((shaft-length 150))
  :components
  ((main-shaft :type 'shaft
               length (the shaft-length))))

(let ((assembly (make-instance 'shaft-assembly)))
  (send assembly main-shaft length)) ; => 150

The component specification supplies length (the shaft-length). The expression obtains a value from the assembly and provides it as the length input of main-shaft. Thus the child's length is determined by the containing assembly's specification; it is not merely the shaft class's initial value of 100.

This is the essential distinction: composition establishes a part–whole relationship; generative composition uses provided-input expressions to establish how attributes of the resulting child are driven by that relationship. The component instance hierarchy and the attribute dependency graph remain different structures.

Adhoc's tests exercise provided input expressions in component declarations. The special symbol adhoc:part, which denotes the child object in that context, is not needed for this introductory example and will be explained when provided-input evaluation is treated in greater detail.

3.6 Inheritance and Shared Semantics

Generative classes also participate in ordinary CLOS inheritance. A derived class can reuse a parent's declared input:

(defobject dimensioned-part ()
  :inputs ((length 100)))

(defobject long-part (dimensioned-part))

(let ((instance (make-instance 'long-part)))
  (send instance length)) ; => 100

Inheritance is one way to share definitions; protocol conformance is another way to share semantic expectations without requiring common class ancestry. We will examine both as the guide develops.

3.7 What These Examples Establish

The small examples demonstrate definitions with inputs, expressions for ordinary attributes, nested components, class inheritance, instantiation, and attribute references. Together they show how a generative object is more than a record of independently stored values: it can contain an executable, declarative model of its properties and parts.

They do not yet establish general rules for explicit assignment, computed-value caching, dependency invalidation, error recovery, transactional consistency, or constraint solving. Those require dedicated treatment and verification. In particular, generalized constraint solving and transactional rollback must not be presented as implemented features merely because they are architectural goals.

Future chapters will expand the relationship among declarative specification, first-class design intent, knowledge-based engineering, and ontology-driven protocols.

3.8 Summary

defobject specifies generative classes through named attributes and components. Inputs provide configurable values; ordinary attributes can declare computed relationships; components declare constituent objects. The defining benefit is not a shorter way to issue construction commands, but a means of encoding and reusing the relationships that govern a design.
