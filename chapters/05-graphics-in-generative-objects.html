Chapter 5 · A visible generative assembly

Graphics in Generative Objects

The preceding chapter introduced spatial relationships between generative objects. This chapter continues the same shaft-and-support example, this time using concrete classes that provide graphical representations. The important programming ideas remain inheritance, inputs, components, and declarative relationships.

Source and scope. The definitions of cylinder_b and prism_a belong to regen-geometry and are intentionally not reproduced here. The shaft-and-support definitions below are taken from the running Regen example, and the pictured assembly is a screenshot supplied from that session. Package imports are assumed, as in Chapter 4. Details of the rendering backend are outside the scope of this introductory chapter.

5.1 Graphical Behavior Through Inheritance

A generative object need not construct its own graphical representation from scratch. It can inherit from an existing concrete class that already provides one. Here, cylinder_b and prism_a are concrete classes provided by regen-geometry. Their geometric behavior and graphical representations are supplied by that library.

The cylinder and box concepts can be specified through protocols, with alternative concrete implementations. For this first graphics example we use particular implementations and defer the protocols' full definitions. Both concrete classes provide spatial behavior, so the concepts introduced in Chapter 4 still apply.

At the implementation level, block-mixin extends node-mixin with graphical grouping support. Readers do not need to work with this grouping mechanism to follow the example.

5.2 Defining a Shaft

The shaft specializes the existing cylinder implementation and supplies a default radius:

(defobject positioned-shaft (cylinder_b)
  :inputs
  ((radius 10)))

No graphical construction commands appear in this definition. The shaft inherits its cylindrical representation and its other cylinder behavior from cylinder_b. It adds one declarative choice: the default radius is 10.

Notice that the shaft definition does not fix its height. That value will be provided by the containing support object, illustrating how a reusable generative object can receive part of its configuration from its context.

5.3 Defining Its Support

The support specializes a concrete prism and contains the shaft as a generative component:

(defobject shaft-support (prism_a)
  :inputs
  ((shaft-length 100)
   (width (- (the shaft-length) 10))
   (length 50)
   (height 50))

  :components
  ((main-shaft
    :type 'positioned-shaft
    center-on (the centroid)
    height (the shaft-length)
    rotation (qrotation (vec3 0 1 0) (/ pi 2)))))

This definition introduces no new object-construction model. Its :inputs and :components have the same roles they had in earlier chapters. What changes is that the inherited classes know how to present their geometry graphically.

The support's width depends on shaft-length. For the default values, the shaft length is 100 and the support width is 90. Its other dimensions are each 50.

The component's provided inputs specify its relationship to the support. height (the shaft-length) makes the cylinder's axial extent equal to the support's shaft-length input. center-on (the centroid) positions the cylinder's geometric center at the support's centroid, with the supplied point expressed in the support's coordinate system. The rotation is a quarter turn about the support's Y-axis, aligning the cylinder's local Z-axis with the support's X direction.

5.4 The Resulting Assembly

Instantiating the top-level support in a running Regen session makes it part of the default scene; because it has graphical representation, the assembly appears in the editor:

(make-instance 'shaft-support)

The accompanying screenshot shows the rectangular support in wireframe and the cylindrical shaft extending through its center. The visual arrangement is a direct consequence of the same declarative definitions used to construct the generative object hierarchy.

As explained in Section 4.1.1, a top-level node can instead be constructed without scene registration by passing :scene nil or 'krma:scene nil.

5.5 Changes Propagate Through Relationships

The shaft-length input plays more than one role. It determines the shaft's height through a provided-input expression, and it determines the support's width through another expression. These are relationships in the generative model, rather than independent measurements copied into several objects.

Similarly, positioning the shaft with center-on avoids embedding a separately computed placement offset in the support's component definition. The cylinder implementation can derive its parent-relative coordinate-system origin using its own local center, dimensions, and rotation.

For a cylinder whose local origin is the center of its base circle and whose axis extends along positive local Z, its local geometric center is halfway along the cylinder's height. The center-on input specifies where that point should be in the parent's coordinates; it is distinct from the parent-relative origin. The point used to position the part and the local origin need not coincide.

These relationships explain why the model is generative: the assembly specifies how constituent objects relate, not just what graphical objects to draw once.

5.6 Looking Ahead

This example deliberately relies on existing graphical implementations. Later chapters can describe the protocols for common blocks, alternatives for positioning by origin or center-on, and presentation controls such as wireframe and shaded views. Those protocols are still being developed, so the present example should not be taken as their complete specification.

A further refinement could define protocols for engineering concepts such as a shaft and its support, distinct from the concrete classes used to realize them. For now, the central point is that ordinary generative-object definitions can acquire visible representations through inheritance while retaining the same declarative relationships.
