Chapter 1

Generative Objects

Regen is a knowledge-based generative programming environment: its objects express declarative relationships, engineering knowledge, and design intent rather than merely sequences of construction steps.

1.1 What Is a Generative Object?

A generative object has a declarative definition: it specifies properties, relationships, and potentially constituent objects without requiring the programmer to prescribe every step used to produce the resulting model. Its declaration may include supplied values and expressions that compute other values.

Consider a mechanical housing whose dimensions depend on the components it contains. A conventional object might store the resulting dimensions. A generative object can represent how those dimensions are derived from its requirements. When the requirements change, the derivations remain part of the model.

1.2 Declarative Description Rather Than Construction Sequence

Declarative programming is a programming approach in which the programmer expresses what properties, relationships, or results are required, rather than explicitly controlling how each step of computation is carried out. An imperative construction sequence might create one piece, assign dimensions, transform another piece, and join them. A declarative generative specification might instead express that “the housing length depends on the shaft length and required clearances.”

Declarative does not mean non-computational or devoid of procedure. Attribute expressions can contain ordinary Lisp computations, and Regen still performs evaluation and geometric operations. The declarative character lies in making the relationships and intended properties of a model explicit, rather than making clients manually orchestrate every update to the result.

These declarations help preserve design intent: the reasons, requirements, relationships, and constraints that explain why a design has its particular properties. A full treatment of design intent—and how to represent and inspect it as a first-class concept—is reserved for later chapters.

1.3 Attributes

An attribute is a named property of a generative object. Some attributes are starting points for computation; others are calculated from surrounding context or other attributes. Components are another kind of attribute, describing constituent objects.

For a cylinder, its length and radius may be given directly, while volume is computed. In a different design, the volume could be the given value and the radius derived from it. The semantic meaning of a property is separate from how a particular class obtains its value.

Chapter 2 distinguishes inputs, ordinary attributes, and components.

1.4 Generative Composition

Complex objects consist of other objects. In Regen, generative composition declaratively specifies constituent objects as part of a parent's definition, rather than treating the child hierarchy as an unrelated assembly step.

A mechanical assembly, for instance, might describe a shaft, bearings, and housing as components. Their properties may depend on values determined elsewhere in the assembly. The resulting instance hierarchy describes containment; it should not be confused with the attribute dependency graph that records computational relationships.

1.5 Generative Objects and Common Lisp

Regen is built around Common Lisp and CLOS. Class inheritance, generic-function dispatch, and object composition remain useful, but generative objects add declarative computed properties and generative assembly semantics.

This is not simply a procedural CAD API wrapped in Lisp syntax. The language's abstraction facilities let a programmer encode reusable engineering knowledge and model relationships explicitly.

Regen is therefore best understood as a knowledge-based system for generative engineering. It uses techniques from knowledge representation: explicit concepts, relationships, and rules. Ontologies provide vocabularies and conceptual relationships; schemas express structural expectations. These are overlapping and related ideas, not a strict mathematical chain of subsets. Later chapters will examine their relationship to Regen's object model and protocols in depth.

1.6 Regen Is a Live Programming Environment

Regen's ambition includes a live programming environment: programs and their objects can be examined and developed within a running Lisp image. A model is not merely a file that produces geometry and terminates.

Live development is useful when exploring relationships. A programmer can examine a running design, change definitions or inputs, and investigate the consequences. Details of evaluation and update mechanics belong in later chapters.

1.7 Expressiveness and Complexity

Declarative relationships do not eliminate complexity. They change where it lives. The system must evaluate attributes, track dependencies, invalidate computed results when appropriate, and report errors when declared relationships cannot be satisfied.

The payoff is that applications can express design intent directly, rather than only encoding the incidental steps of one construction. A reusable abstraction can eliminate repeated construction procedures across many models. The cost is a more sophisticated generative runtime.

1.8 Summary

Generative objects express properties and composition through reusable declarative specifications that can preserve design intent. They are grounded in Common Lisp's object system but include computational relationships not captured by ordinary stored properties alone. The next chapter introduces three essential attribute kinds found in generative Regen objects—inputs, ordinary attributes, and components—and explains protocol-based interoperability. The attribute system is extensible; these are not the only possible kinds.
