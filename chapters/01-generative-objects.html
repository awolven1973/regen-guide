Chapter 1

Generative Objects

Regen is a knowledge-based generative programming environment: its objects express declarative relationships, engineering knowledge, and design intent rather than merely sequences of construction steps.

1.1 Generative Objects

A generative object has a declarative specification in Regen. This specification defines a class, its attributes, their relationships and also its constituent subobjects. Instead of describing "how" each step of the computation is carried out, one describes "what" is being computed. The reason why it is called generative is because querying the instance tree for attribute values will compute those values and subobjects on demand. Ordinary objects in OOP usually do not do this. When they do, the code is usually procedural as opposed to declarative. The object definition itself reveals the purpose of the design of the model, whether it be a physical machine, a GUI, or an abstract computation.

1.2 Declarative Descriptions Rather Than Construction Sequence

Consider a mechanical housing whose overall structure depend on the size and layout of the components of the overall assembly. Declarations can be made to express these relationships. A generative object definition can produce the binary code to compute the chain of dependencies in the correct sequence regardless of the order of the source code declarations. This allows the programmer the ability to arrange, group, and layout the source code in a way that defines intent rather than procedure. The specification is not devoid of procedure, rather, procedure is specified in small chunks called "expressions" or "attribute expressions".

1.3 Attributes

An attribute is essentially a named property of an object. Some attributes are starting points for computation, these are called inputs. Other attributes provide expressions for computing values, these are considered ordinary attributes. And other attributes describe child subobjects and their relationship to the parent object. These attributes are called components. This partitions attributes of generative objects into three essential kinds, but there exist other attribute kinds as well, both for generative and non-generative objects.

1.4 Protocols

A cylinder type may be specified from its height and a radius, and its volume is computed, while another cylinder type may be specified by its volume and radius, and its height is computed. These are two classes of cylinders where "height", "radius" and "volume" have the same semantic meaning, but the kind of attributes used in their definitions are different. "Cylinder", therefore, describes a protocol for these round objects with flat ends. Functions can then be defined to handle objects of a certain protocol rather than objects of a prescribed concrete datatype, whether or not the classes of the objects have commonality in their inheritance trees. Use of these "protocols" allow parts to be used somewhat interchangeably, and the actual type of object is computed from the context.

1.5 Regen

Regen is best understood as a knowledge-based system for engineering. It follows in the ICAD tradition, an engineering system used in the 1980s and '90s. Knowledge-based systems are a kind of knowledge representation system that uses rules to embedded in the knowledge to execute programs, and are somewhat related to expert systems and prolog. Expert systems generally treat the knowledge as passive and use inference engines and reasoners to compute solutions and update the knowledge. KBE may also be built from a prototype system (or "frame" system), where there is no distinguishing between a class and an instance, however Regen is a class/instance system based on the Common Lisp Object System. KR systems including KBE form ontologies, which provide vocabularies and conceptual relationships which describe schemas and taxonomies. Regen is, however, in a nutshell, just Object Oriented Programming, but since it is Common Lisp, one can use nearly any programming style to augment it.

1.6 Live Programming Environment

Regen is a live programming environment, meaning programs and their objects can be examined, experimented with and definitions can be changed while the program is running. This is also called image-based development and has been a hallmark of Common Lisp for decades. Images can be created and saved and reused. Incremental changes are key. One does not have to shutdown the system to make changes, and then script a restart to return to the next experiment. There are limitations, but Regen aspires to reduce these limitations.

Live development is used in other engineering environments, like Mathematica, and provides a high level of flexibility and more rapid design iterations, but also must be maintained with care.

1.7 Expressiveness and Complexity

Declarative relationships do not eliminate complexity, but they change where it lives. The system automatically evaluates attribute definitions, tracks dependencies between values, and invalidates computed results and reports errors when an instance of a generative class is computed or reconfigured. Complexity can be difficult to manage, but Regen provides tools for abstraction with explicit contracts. Abstraction is key to avoiding duplicating code and providing generic operations.

1.8 Summary

A generative object is specified declaratively through its attributes, the relationships among them, and its constituent subobjects. Attribute expressions compute values and components on demand, while dependency tracking allows the system to evaluate relationships independently of declaration order and respond to reconfiguration. Inputs, ordinary attributes, and components are three essential attribute kinds, but they are not the only kinds.

Protocols give attributes consistent semantic meanings across different implementations, allowing objects to be used interchangeably even when their classes do not share an inheritance hierarchy. Regen applies these ideas to knowledge-based engineering in the ICAD tradition, using Common Lisp and CLOS while remaining open to other programming styles. Its live, image-based development environment supports inspecting, modifying, and experimenting with running models. Declarative programming does not remove complexity; it makes abstraction, explicit contracts, and careful management of dependencies especially important.
