Chapter 2

Attribute Kinds and Object Protocols

Declarative attributes encode properties and relationships in a generative object; protocols establish shared semantics across otherwise unrelated object classes.

2.1 Named Properties of Objects

An attribute identifies a property of an object by name. A declarative definition can specify how that property relates to other properties without prescribing a manual update sequence. In a generative system the property's meaning is distinct from the way its value is supplied or calculated. For example, width can mean the same geometric dimension whether the value is entered directly or derived from other dimensions.

This chapter introduces the three essential attribute kinds in generative Regen objects: inputs, ordinary attributes, and components. These are foundational categories, not an exhaustive enumeration. The attribute system can support many additional kinds, each with its own semantics. Here, kind refers to an attribute category, not to a Common Lisp type or class.

2.2 Inputs: Starting Points for Computation

An input is an attribute that serves as a starting point for computation. Inputs make a generative definition configurable: two instances of a class may use different input values while sharing the same computational relationships.

An input need not always lack a default expression. An optional input can obtain a value from its declared expression until an explicit value is supplied. The finer details of assigned versus computed values belong in the attribute-evaluation chapter.

2.3 Ordinary Attributes: Computed Properties

An ordinary attribute ordinarily expresses a derived property. A cylindrical part might derive its volume from radius and length; an assembly might derive an envelope from its constituents.

Computation does not mean the value is necessarily immutable. Some ordinary attributes can be explicitly assigned. For those attributes, it is important to distinguish the computed expression from an assigned override; details of assignment and invalidation are deferred.

2.4 Components: Specifying Nested Objects

A component describes a constituent generative object. Components can specify the class of a child and the values or relationships that determine the child's properties.

Think of a shaft assembly containing bearings, a housing, and a shaft. Its composition is part of the model's description; the resulting child objects form an instance hierarchy. This use of the word component is not the entity-component-system (ECS) notion of a component.

2.5 Inheritance and Composition

Inheritance and composition solve different problems. Inheritance allows a CLOS class to specialize or reuse behavior and attributes from other classes. Composition builds a larger model out of constituent objects.

A bearing is not a specialized shaft simply because both belong to a shaft assembly. They can be composed without having an inheritance relationship. Conversely, several bearing classes may share an ancestor while appearing in very different assemblies.

2.6 The Same Property Can Be Specified Differently

One class may treat length as an input, while another derives length from other properties. Both can provide a property with the same meaning even though its attribute kind differs.

That flexibility is central to protocols. It allows clients to rely on a conceptual property without requiring every implementation to compute or store it in the same way. The shared meaning can help express design intent independently of an implementation strategy.

2.7 Object Protocols

An object protocol defines a semantic contract: properties or operations, their meanings, and the expectations on implementations. Unlike a common superclass, a protocol does not necessarily require CLOS classes to share an inheritance ancestor.

For example, two classes representing different sorts of geometric entities might both provide meaningful bounding dimensions, despite using different underlying geometry. Consumers can program against the shared contract, rather than a single concrete representation.

Protocols should declaratively describe what a property means, not mandate unnecessary details of how each class computes it. An external backend can satisfy a protocol by mapping its native operations onto the required semantics. Protocols can also form part of a larger knowledge representation, where concepts and relationships are described independently of particular implementations.

2.8 Families of Generative Objects

Generative objects can form reusable families through inheritance, composition, and shared protocols. A family may provide variations in geometry, construction, or computation while preserving the properties on which clients depend.

In a configurator, a component's concrete class may be chosen according to design context. The parent can express the role and required properties of its child without hard-coding every possible implementation.

Separate questions—whether an object is a member of a class family, whether it is a component of another object, and whether its attributes depend on other attributes—must not be conflated.

2.9 Summary

Inputs, ordinary attributes, and components are three essential attribute kinds used in generative Regen definitions, not the only kinds that can exist. Additional kinds may capture other attribute semantics. Inheritance and composition support reuse in different ways, while object protocols let independently implemented classes satisfy a common semantic contract.

Later chapters will explain concrete defobject syntax, attribute dependency tracking, consistency, and geometry in detail.
