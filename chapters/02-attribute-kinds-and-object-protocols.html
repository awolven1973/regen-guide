Chapter 2

Attribute Kinds and Object Protocols

Attributes give generative objects named properties with shared meanings. Their kinds determine how values are supplied, computed, maintained, and passed to constituent objects.

2.1 Attributes: Named Properties of Objects

In Regen, properties of objects are made explicit by giving the property a name and a definition. An attribute's meaning is independent of the way a value is supplied or computed. It may be of any attribute kind, because it is accessed identically to any other attribute. It is not necessary to define in code the meaning of an attribute, but it should be included in the documentation. The meaning derives from the name and how it is used in a context. The meaning across objects is therefore implicit, but can be gleaned from its various definitions. For instance, in a box-shaped object protocol, width, length and height all have a particular meaning and should be coded to return compatible types, such as some kind of non-negative real number. In a family of objects based on circles, spheres or circular arcs, radius and center have a shared meaning. For beziers and b-splines, control-points have a similar meaning. For a higher level object, such as a ground vehicle, you may have engine, drivetrain and wheels conform to a particular meaning. Reusing attribute names is a form of abstraction that allows for greater flexibility and genericity to the system. It is an art, however.

This chapter explains the three essential attribute kinds that can be used to define an attribute in a particular class. Different classes may be used to support a protocol. It is not necessary to lump all the possible code for initialization, computation, reinitialization, and dependency management of an attribute of a particular name into one class. Doing so only makes the code bug prone and hard to follow. Generative objects are referenced through chaining messages; therefore, an object's identity is less important than its protocol.

2.2 Inputs

As discussed before, an input is an attribute kind that serves as a starting point for a computation. There are different kinds of inputs. A required input is one where either the user supplies a value, or the value of the input is supplied by a parent object. It is an error for executed code to reference a required input whose value has not been supplied.

Optional inputs are another kind of input and have a default value which is supplied by the execution of the attribute expression when the value is not supplied.

Inputs are always settable, regardless of the depth in the generative tree an instance may be. They use a spreadsheet-cell like model. If the input is explicitly set, that's its value and it "sticks" until someone changes it. Inputs can be changed with a "setf" expression. If the input has a "formula" (i.e. attribute expression) it is computed from that. But if it is "set" (through intialization or explicit setf) the value provided "sticks" and the formula is no longer used. You can unbind an input. This means the value is removed, and the "formula" semantics will be restored, or error if used and there is no formula.

A visual input can be based on any kind of input. The visual declaration is used as a hint to the dependency maintenance protocol that it should redraw dependent graphics when the input is set or unbound. The graphics in Regen are live, unlike previous generations of Lisp KBE-systems. This means that refresh happens incrementally at any time rather than a global redisplay of the whole tree in a browser window.

2.3 Attributes

An ordinary attribute expresses a derived property. It has an attribute expression which computes the value. There are other kinds of ordinary attributes. An uncached attribute has no storage. It is computed every time it is referenced and simply passed over in dependency management.

A modifiable attribute is different than a regular attribute, it is settable, but distinct from an input. It has an attribute expression, but that is only used if the attribute is referenced before it is set the first time. A modifiable attribute is used as a state variable in a generative tree. For instance, it may be used to count the number of iterations of some computation that has been performed on the object. A modifiable attribute participates in dependency management, but unlike an input, it is not initializable at instance creation time, that is, it has no initarg.

2.4 Components

A component attribute describes a nested generative object. A component provides a means of composing a class, but is not the same as a component of an entity-component-system. Component attributes can compute or otherwise specify the type or protocol of the object being generated. They also specify "provided" inputs. A provided input is a specification to compute or supply the value of an input for a subobject. Provided inputs are essential in making classes flexible and reconfigurable. Components can also be aggregate components, which require an index or key to message individual members. Notable types of aggregate components include table and array aggregates. Aggregate components will be discussed in more detail in later chapters.

2.5 Summary of Chapter 2

An attribute is a named property whose meaning can be shared across otherwise different classes and implementations. The kind of attribute determines how its value is obtained or maintained, not how other objects reference it. Protocols establish common meanings for attributes, letting programs operate on objects through shared contracts rather than requiring a single concrete class or inheritance hierarchy.

Inputs, ordinary attributes, and components are three essential attribute kinds in generative objects, with further variations and additional kinds available. Inputs support explicit values, optional expressions, assignment, and unbinding; ordinary attributes compute derived values, while uncached and modifiable attributes have distinct evaluation and state semantics. Components specify nested generative objects and their provided inputs, allowing a parent's definition to determine the configuration and composition of its subobjects.

Together, these mechanisms allow Regen to describe reusable, configurable models through relationships among named properties. The next chapter will show examples of defining generative object classes and their attributes with `defobject'.
